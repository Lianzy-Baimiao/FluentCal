# FluentCal 0.3.26 — Windows 窗口调整性能更新

- 拉动日历边框时，不再因为窗口高度变化重建“所有”列表的整份任务历史。月历和多周视图仍按新高度布局；真正修改任务或筛选条件时，列表照常更新。
- 拖动或缩放进行中，不再每移动一步就投递一次显示器枚举任务。松手后更新托盘的屏幕选择，跨 DPI 时仍即时处理缩放变化。
- 显示配置变化后的延迟归位不再把正在拖动的日历拉回旧位置。先保存松手时可达的位置，再处理挂起的恢复；旧窗口或上一次拖动的结束通知不会覆盖新位置。

## 实测结果与边界

在 GitHub 托管的独立 Windows 测试机上，对正式版 `0.3.25`、最终交付的 `0.3.26` EXE 和普通不透明窗口重放同一组鼠标轨迹。平移只改变位置，缩放只拖底部手柄。每个条件三轮；下表为各轮 P95 的范围，单位毫秒。窗口边界读自 Win32；画面边缘来自 DXGI 合成帧，不含物理显示器延迟。

| 条件与指标（默认 CPU） | 0.3.25 | 0.3.26 |
|---|---:|---:|
| 长历史列表缩放：输入到窗口边界更新 | 30.75–34.23 | 4.82–15.73 |
| 长历史列表缩放：输入到合成画面边缘 | 76.67–81.51 | 56.90–71.81（两轮有效） |
| 月历同屏平移：输入到合成画面边缘 | 30.24–31.79 | 28.79–30.16 |
| 月历缩放：输入到合成画面边缘 | 48.20–59.28 | 47.32–66.58 |

普通窗口平移的对照为 29.42–31.55 ms，没有测出日历特有的持续平移延迟。普通窗口缩放为 31.99–35.02 ms，月历缩放的画面仍然较慢，不能宣称所有视图都已消除卡顿，也没有证据把差异归因于反馈者的显卡。不能可靠识别像素边缘的样本不算零延迟。

只让被测进程使用一个逻辑核时，长列表缩放的合成画面 P95 从 76.69–78.59 ms 降到 50.16–63.76 ms（三轮均有效）。[最终 EXE 对照](https://github.com/Lianzy-Baimiao/FluentCal/actions/runs/46006657495)、[最终 EXE 单核对照](https://github.com/Lianzy-Baimiao/FluentCal/actions/runs/46006662563)、[源码构建对照](https://github.com/Lianzy-Baimiao/FluentCal/actions/runs/46004404027) 均通过。Rust 工作区 274 项通过、0 失败、9 项默认忽略；前端 237 项通过，类型检查、构建和翻译检查通过。
