# 不占用桌面输入的窗口回归

这些测试从 `native` 目录运行。它们不启动已安装的 FluentCal，不发送 Windows 鼠标或键盘消息，也不改变显示器配置。隐藏桌面和登录会话仍可能共用系统光标，不能用隐藏桌面代替虚拟机来驱动原生移动循环。

## 长列表缩放

```powershell
cargo test --locked --offline -p fluentcal-native --test e2e -- --exact resizing_list_keeps_its_rows_until_data_changes
cargo test --release --locked --offline -p fluentcal-native --test e2e -- --ignored --exact replay_long_list_resize_in_memory --nocapture
```

第一条用 Slint 测试后端改变窗口高度：确认尺寸回调确实更新了可用高度，但没有重新生成或比较任务列表。真正改变“显示已完成”仍必须刷新列表；切回月/多周视图时，周行仍必须填满新网格。

第二条用生产软件渲染器把解锁状态下的日历绘制到进程内的 RGBA 缓冲区。合成数据是 40 个每月待办、每个 36 条完成历史，“列表 → 所有”、显示已完成、开启自动行高。宽度保持 1800 像素，高度从 1100 像素起，每步 14 像素，12 步往返三轮，共 72 帧。每步都检查真实容量回调，最后检查列表行数和非空图像；输出尺寸处理耗时、含绘制的整帧耗时及最后一帧像素摘要。

要对照旧版，在单独的 `v0.3.25` 源码副本中使用同一份 `native/app/tests/e2e.rs` 测试文件，产品代码保持原样。在同一机器、日期及字体环境下各自构建并保留测试二进制，交替运行。先确认旧版结构断言失败、修复版通过，再比较行数及最终像素摘要一致的样本。耗时用于对照，不作为 CI 的固定阈值。

2026-11-27 的解锁状态样本：2,493 行，两个版本各三轮。每轮的离屏整帧 P95 在 `v0.3.25` 为 18.648–27.448 ms，修复后为 12.111–12.693 ms；六轮最终帧的 RGBA 摘要均为 `3f4ef0f18db56691`。

## 显示配置变化后拖动回跳

```powershell
cargo test --locked --offline -p fluentcal-native --lib -- platform::placement::tests
cargo test --locked --offline -p fluentcal-core --test layout
```

纯内存回放覆盖：旧位置 `(80,80)` → 开始调整 → 拖到 `(200,110)` → 延迟恢复到达 → 松手保存。恢复不得在手势中、或退出消息已排队但新位置还未保存时覆盖位置。重复恢复合并；上一次手势的退出不能结束新的手势。若松手时原屏幕已断开，不可达的矩形不能被存为新位置。

## 能证明什么

另有手动触发的 GitHub Actions 工作流 `Windows window motion`。它只在 GitHub 托管的独立 Windows 测试机发送鼠标输入；在开发者电脑上，`python scripts/window-motion.py --self-test` 只验证离线算法，实际输入入口会拒绝运行。用相同的往返轨迹分别移动窗口、拖底部手柄，与普通不透明窗口对照。它核实原生移动循环、实际达到的尺寸、返回位置，并分别记录光标、Win32 窗口边界和 DXGI 合成像素的呈现时间；不能识别像素边缘时不给画面延迟数字。Windows 合成时间不含最后的物理显示链路。

内存帧时间不是物理鼠标到屏幕亮起的延迟。显示器始终不变、只平移不缩放的情况，也不能用长列表缩放的数据定性。若反馈者在该条件下仍能复现，应在反馈机上由本人操作、只读记录光标和窗口边界的相对位移，或在有独立输入的 Windows 来宾系统验证。要评价实际呈现，还需含光标的画面或显示链路测量。
